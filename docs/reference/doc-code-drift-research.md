## 1. 现有方案格局

三个技术流派 + 一个"要不要 RAG"的规模决策层。

### 1.1 自底向上·纯静态 AST 符号图谱(不用 LLM)

| 方案 | 定位 | 存储 | 检索 |
|---|---|---|---|
| **CodeGraph** | AI 编程降本(-35% token/-70% 工具调用) | SQLite + FTS5(nodes/edges/files/unresolved_refs) | FTS5 倒排(精确、亚毫秒、稳定性) |
| **GitNexus** | 深度关系分析/跨仓库影响 | 嵌入式图库 KuzuDB(Cypher) | BM25 + 向量 + RRF 三路融合 |

共性:**tree-sitter 增量式静态解析**(11~20+ 语言),提取 calls/references/extends/implements/contains/imports 边,MCP 暴露 explore/callers/callees/impact/detect_changes,"预计算 + 单次查询出结论"。索引期与分析期都**不碰 LLM**,天然确定性。

### 1.2 自顶向下·LLM 语义图谱

- **Understand-Anything**:唯一引入运行时 LLM 做语义摘要,6-Agent 流水线(project-scanner→file-analyzer 5并发→architecture-analyzer→tour-builder→graph-reviewer→domain-analyzer),产出含 summary/tags/Layer 的 `knowledge-graph.json`。**唯一同时索引代码 + 文档(wiki)**、视角最贴近人写文档的"架构意图"。RocketMQ 评测均值最高(80.9%),因索引视角与文档来源视角最接近。

### 1.3 混合 RAG / 知识图谱增强

- **ctx-sys**:向量(snowflake-arctic-embed-xs 384维)+ FTS5 + 图谱三路 Hybrid,RRF 融合。但实测≈baseline——**索引的是代码符号无语义摘要**,与自然语言 query 语义距离大。
- **Neo4j 知识图谱增强代码生成**(2712884923):人工 8 类实体 + 6 类关系,AI 采纳率 73.29% vs 无图谱 42.05%。但**纯人工构建 + 被动更新**。
- **业界案例**(2725725083):美团终端 Codebase 检索(RAG,准确率仅 40-46%)、阿里 **Qoder Repo Wiki(自动检测代码变更→提醒更新 Wiki)**、GitMCP(按需构建不预索引)。

### 1.4 规模决策层(要不要 RAG)

《RAG 边界调研》(2767825131)+《美团 Java Workflow》(2771606850)一致阈值:

- **≤100 篇** → 导航式 INDEX.md
- **≤200 篇** → Skill 渐进加载
- **>200 篇** → BM25(0.3) + 向量(0.7) + Cross-Encoder Rerank
- **多跳依赖** → GraphRAG

## 2. 对本项目的关键启示(可直接借鉴)

### 2.1 【最重要】找线索 vs 做判断必须分层

《美团 Java Workflow》(2771606850)核心方法论:**"找线索(图查询/静态分析,确定性)与做判断(LLM 语义)必须分开,叠加给同一 LLM 是误报不稳定的根本原因"**。落到 drift:

- **定位层(确定性)**:AST/FTS5 精确锚定"文档声明的实体 ↔ 代码事实"的对应关系。
- **判定层(LLM)**:只在已对齐的符号对上判断"是否一致",带分层置信度。
- 呼应 2765099516 坑 #1/#4:不要用纯向量相似度判定一致性。

### 2.2 代码结构提取:复用现成图原语

- 变更影响分析:GitNexus `detect_changes` + `impact`、CodeGraph `impact/trace/callers/callees`。drift 核心动作 = "改了代码 X → 哪些符号受影响 → 反查哪些文档描述了这些符号 → 判定过期"。
- AST + 调用图作代码真值,比纯文本 diff 更能精准定位"哪段文档对应哪段代码"。
- 引用解析三层策略:框架特定(Spring @Autowired/@RequestMapping)→导入→全局名称匹配。

### 2.3 文档侧表征:用自顶向下 LLM 语义图谱

drift 本质 = 比对**文档(自顶向下架构意图)vs 代码(自底向上实现)**。Understand-Anything 式含 summary/tags/Layer 的语义图谱最贴文档视角(均值 80.9%),适合作文档侧代码表征基线。甚至可把"自动生成文档 vs 人工文档"比对本身当 drift 信号。

### 2.4 drift 分类:直接用四态模型

《美团 Java Workflow》(2771606850)"读取≠采纳"四态可原样迁移:

- 文档有 ∧ 代码有(一致)
- 文档有 ∧ 代码无(**规约失效/文档过期**,drift 主战场)
- 文档无 ∧ 代码有(**知识缺失**,2712884923"完备性即正确性",别人易漏)
- 都无

其 **Phase D.5 spec-drift-checker**(以 spec 为 ground truth 逐条核对 SC/FR 覆盖,非阻塞产出)是现成 drift 范式。

### 2.5 索引保鲜(低成本感知变更)

- CodeGraph 三层新鲜度:FSEvents/inotify 监听 + 2s 防抖 + (size,mtime)+ 内容哈希检测离线期变更并补建。
- git hash 对比 HEAD,只重分析变更批次(Token 约全量 5-15%).
- **"过期横幅"降级**(2770231312):同步中文件在响应前加 ⚠️ 横幅告知直接读原文件,避免静默返回过期数据—drift 检测器自身也要有这个能力。

### 2.6 评测飞轮可复用指标

- 编辑距离(Levenshtein)相似度 + A/B 对比(有图谱 73% vs 无 42%),但需辅以 AST 结构级比对(编辑距离对重命名/等价改写误判).
- 三级 Grader:Code grep/AST + Model llm_judge(3票)+ Human 金标(Kappa≥0.7);asyncio+Semaphore 并行;Wilson CI / McNemar 配对。
- RAG 自愈:相似度 <60% 触发代码搜索→LLM 提炼→写回(0.567→0.792),可迁移为 drift 自动修复闭环.

## 4. RAG 边界警示(用在哪 / 不用在哪)

**不该用 RAG:**

- **代码↔文档精确对齐**:路径/符号名已知的精确匹配,用 grep/FTS5/AST,不用向量(2765099516 坑 #4).
- **规模 <100-200 篇/文件**:INDEX.md 导航 + 按需 Read 即可.
- **不要对 md 直接切 chunk 做 RAG**:破坏章节结构、召回片段语义不完整。

**该用 RAG / 图谱:**

- 跨 session 模糊语义回忆、长尾历史知识(MD 注入高频 + RAG 长尾).
- 多跳依赖追踪(A→B→C):GraphRAG 使 P@5 从 17.7%→49.1%.
- 补充召回(向量只作 FTS5/AST 之外补充,不作判定依据).

**真值原则**:Markdown/代码是 source of truth,向量库/图谱是**可重建的派生检索层**。检索层坏了可重建,别把结论绑死在派生层。

## 5. 差异化确认(护城河)

**业界有没有在做 doc-code 一致性检测?—有零星"雏形",但无独立完整闭环。**

| 已有相关动作 | 出处 | 完成度 |
|---|---|---|
| Qoder Repo Wiki 内置"自动检测":代码变更→提醒更新 Wiki | 2725725083 | 产品化样板,但绑定 Wiki 生成产品内,非独立 drift 系统 |
| 方向二:Code PR 阶段"文档检测智能评审机器人" | 2725725083 | **最接近本方案的落地路径,但仍是"设想",非成熟系统** |
| Phase D.5 spec-drift-checker(spec↔实现) | 2771606850 | 是 spec-code drift,非 doc-code;可借范式 |
| Understand-Anything 同时索引代码+文档 | 2765099516 | "联合理解"底座;**不做一致性判定** |
| GitNexus Wiki 自动生成 | 2757288028 | 生成基线,**未做 drift 判定/评测集** |

**结论:护城河成立。** 现有方案要么只做代码侧图谱(GitNexus/CodeGraph/ctx-sys,无文档解析/对齐/阈值/评测集),要么把 drift 当附属提醒(Qoder),要么停留在设想(美团方向二)。**没有人把"AST 锚定 + LLM 语义比对 + Multi-Agent + 评测飞轮"组合成独立 doc-code drift 系统。**

**差异化打法(万一有人先做):**

1. **确定性对齐 + 分层判定**(2771606850),而非"单次工具调用乐观出结论"或"纯 RAG 召回"—可信度差异。
2. **评测飞轮**是最难被复制的部分:三级 Grader + 分层评测集 + A/B 范式 + denom_max 防作弊。把"检测器本身可信"做成核心资产("先修评测再改 Agent").
3. **四态完整覆盖**:不仅检"文档与代码冲突",还检"知识缺失"(文档无∧代码有)—2712884923 证"完备性即正确性"。
4. **嵌入 PR 门禁 + 事件驱动**:保存文件/PR/CI failed/Release 触发(2725725083 方向二 + 2746384780),做持续同步闭环而非一次性扫描。

## 缺口1:文档侧结构化事实抽取(材料充分)

**确定性谱系(从高到低)**:

- **代码侧 AST 骨架**:OpenViking(km 2756034031)`tree-sitter` 提取 `CodeSkeleton/FunctionSig/ClassSkeleton`,含 docstring 首行/import/签名;`code_summary_mode` 三档 `ast`(纯确定,≥100行跳过LLM)/`llm`/`ast_llm`;原则**"Parser 不调 LLM"**(与本项目定位属同款)。→ **代码侧直接复用此 schema 当骨架基座**(代码解析非重点)。
- **文档侧围栏/正则**:GBrain(km 2765788859)`## Facts` 围栏 + 确定性 reconcile,零 LLM 但格式依赖。
- **LLM+schema+校准**:注入测评(km 2770294827)L3 声明抽取,LLM 抽三元组 + JSON schema + 人工校准门槛(一致率>90%、多次不一致<1.5%)。**事实判定用确定性二值语言,LLM-as-judge 仅语义解析不参与"事实判定"**。
- **生而结构化**:策略5(km 2772176702)产物生成端强制 schema + `_schema` 版本号,从根上消除事后解析。

**文档侧三层解析样板**(km 1286970074,最贴合本项目):结构层(heading+代码块title定位)/类型层(字段三元组)/注释层(必传、枚举名藏在注释和title里,是需抽取区)。

**关键坑**:绝不依赖 heading 序号定位—该 API 文档自身就有编号 drift(2.2.2 应为 2.1.2),必须用 heading 文本+代码块 title。

## 缺口2:符号对齐(部分充分,需自补)

**已有零件**:

- KnowledgeManus(km 2708137250)渐进回退链:精确名→符号名→构造ID→模块;FQN 规范化 `class:module.path:ClassName`;处理导入别名/相对导入。
- 作用域消歧(km 1286970074):同名 `ServiceStatus` 两个枚举名,必须结合"所属方法"消歧。**对齐单元=方法/类作用域内声明,非全局名字**。
- 别名映射(km 2769059822):`userQuery/question/q`→标准 `query`,多别名+标准名模式。

**材料不足**:重命名追踪(git history)、签名指纹、embedding 语义对齐无直接方案,需基于工程经验自补五级回退链(精确名→FQN→签名指纹→embedding→LLM裁决)。

## 缺口3:真值哲学(材料最充分,纠正 arch 隐患)

**核心收敛**:

1. **信源本身会 drift**(km 2772176702):存在≠正确、语法契约≠语义契约、信源会变成第二真相源、四道独立防线:存在性/语法有效/语义合理/与代码同步。→ **纠正 arch §3"真值是代码和文档本身"的不完整**。
2. **按文档类型区分真值方向**(km 376430639 + 1286970074 收敛):凡能从代码机械派生的文档(API/IDL/签名表)→ 代码为准,drift=文档落后;非派生型(设计/需求)→ 文档为准或双向。→ **arch §4.3 四态全隐含"代码为准",对设计文档是错的,需按类型分叉处理**。
3. **避免循环验证**(km 2770294827):LLM 只解析语义,确定性规则判 drift,不"用 LLM 验 LLM 抽取结果"。
4. **三层真值**(km 2765788859):原文(永久)/知识页面(当前)/派生索引(可重建)。

## 缺口4:反向索引(材料不足,需自建)

**最弱缺口**。12 篇无符号级 code→doc 反向索引,只有:

- repo 级正向链路(km 1286970074):appkey/gitPath→解析→一批API文档,定位不到字段级。
- 代码内部影响图(km 2708137250):只有 CONTAINS/CALLS/IMPORTS/INHERITS,无 code→doc 边。
