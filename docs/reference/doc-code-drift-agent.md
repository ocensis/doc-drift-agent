# Doc-Code Drift Agent — 第二个求职项目方案

> **历史方案（已归档）**：本文保留早期 Multi-Agent/RAG 设计，只用于追溯决策，不代表当前架构。请以 [2026-07-12 主设计](../superpowers/specs/2026-07-12-doc-code-drift-agent-design.md) 为准。

> 一个自动检测「文档与代码是否对得上」的 Agentic 系统。
> 定位:求职作品(广投大厂 agent/应用岗),与 SCA 项目互补,补齐 RAG / Multi-Agent / Memory / 评测飞轮四项 JD 硬通货。

---

## 0. 一句话说清这是什么

**自动揪出"文档在骗人"的地方。**

给它一个代码项目(如某个开源库),它逐条比对文档描述与代码实现,输出一份"文档健康报告":
- 哪些文档**过时**了(文档说 `login(user, pwd)`,代码已改成 `login(user, pwd, otp)`)
- 哪些文档**自相矛盾**(两处对同一概念说法冲突)
- 哪些代码**没有文档覆盖**(新增的公开接口文档只字未提 = 知识盲区)

它不是"文档问答"(那只管找得到,不管对不对),它是文档问答的**上游质检员**——先保证知识是对的。

## 1. 为什么做这个(选题论证)

### 1.1 为什么不是"文档问答 Agent"
纯文档 RAG 问答**没有护城河**:Context7 已是标品,字节 OpenViking / 美团魔改版 + 通用 agent(OpenClaw/Claude Code)已完全覆盖日常查询,做一个"带 agent 的 context7"— 命中 0 条护城河 = 套壳。

### 1.2 护城河在哪
护城河判定四条(通用 agent 天然拿不到,命中 ≥1 条硬的才有意义):

| 护城河 | 本项目是否命中 |
|---|---|
| ① 私有上下文 | 中(接真实代码仓的结构化解析) |
| ② 领域 workflow 固化 | ✅ 文档保鲜 SOP 编排化 |
| ③ 有状态积累 | ✅ drift 历史 / 盲区追踪 / 数据飞轮 |
| ④ 垂直深度 | ✅ **doc-code 语义级 drift 检测引擎** + 核心壁垒 |

关键:**"查文档"通用 agent 能做;"逐条比对整个项目的文档与代码、精确找出所有不一致"它做不到**——这需要真正解析代码结构(函数签名/返回类型/配置项),是专门的分析引擎,不是聊天能蹦出来的。

### 1.3 为什么正好适合我
- **SCA 项目**:扫描整个代码项目 → 找出代码里的 **bug**
- **本项目**:扫描整个代码项目 → 找出**文档与代码对不上**的地方

同一套"读懂整个代码项目结构"的静态分析肌肉,**换个靶子**:SCA 找 bug,本项目找文档谎言。能力同源,产出不同 → 两个项目互相印证、不重叠。

### 1.4 行业背书(意义题免答)
美团《如何低门槛低成本搭建一个"好用"的知识库》(km 2758494864)已把"知识保鲜/毒库治理/偏差飞轮/健康度指标"作为战略方向系统落地。**说明这是大厂正在投入的问题**。但其"一致性保鲜"靠事件驱动 + 人工审核,**没有一个自动化的语义级 drift 检测引擎**——这正是本项目做深的缺口。

### 1.5 差异化定位(经 10 篇学城调研确认,详见 doc-code-drift-research.md)
业界/美团内部在"代码知识库/理解"上已高度成熟,但**没有人把 doc-code 一致性检测做成独立闭环**:

| 现状 | 代表 | 缺什么 |
|---|---|---|
| 只做**代码图谱/检索** | GitNexus, CodeGraph, ctx-sys | 完全没有文档解析、doc-code 对齐、drift 阈值、评测集 |
| drift 当**附属提醒** | 阿里 Qoder Repo Wiki | 绑定在 Wiki 生成产品内,非独立系统 |
| 停留在**设想** | 美团调研"PR 文档评审机器人"(km 2725725083 方向二) | 只是方向,无成熟系统 |
| spec-实现 drift | spec-drift-checker 类范式(以 spec 为准逐条核对实现) | 是 spec-code,非 doc-code;可借范式 |

**本项目 = 独立 doc-code drift 检测 + 评测飞轮**,填的正是上表空白。护城河成立。

## 3. 技术选型(已锁定)

| 维度 | 选择 | 理由 |
|---|---|---|
| 语言 | **Python** | 广投大厂、个人 Python 强、精力压在深度上(非美团专属才选 Java) |
| Agent 框架 | LangGraph(编排/状态图) | 主流、贴 supervisor/handoff 心智 |
| **代码解析(核心)** | **tree-sitter**(多语言、增量、容错 AST)+ Python AST 起步 | 复用 SCA 肌肉;tree-sitter 是 GitNexus/CodeGraph 统一底座(research §1.1) |
| **符号索引(核心)** | **SQLite + FTS5 倒排**(精确、亚毫秒、确定性) | doc-code 精确对齐要的是确定性匹配,不是相似度(见 §4.1) |
| 检索后端(**派生层**) | 轻量开源向量库(Chroma/Qdrant)+**仅作补充召回** | 见下方"检索定位"——不是核心,可重建 |
| LLM | 可换(Claude/DeepSeek/开源) | 仅用于**判定层**语义比对(见 §4.2) |
| 知识来源 | 一个真实开源项目的 docs+源码为主,Obsidian 作为更多源 demo | drift 引擎需要"文档有对应代码"可验证 |

**⚠️ 检索定位(调研修正,research §4 铁律)**:

- **真值是代码和文档本身**——但**信源本身也会 drift**(存在≠正确、语法对≠语义对),需四道独立防线校验,见 §4.7。FTS5/AST 索引与向量库都是**可重建的派生检索层**,结论不绑死在派生层。
- **doc-code 精确对齐用 FTS5/AST/grep,不用向量**——已知符号名时向量反而引入噪音(research 坑 #1/#4)。
- 向量 RAG **只在**长尾语义回忆、跨 session、多跳依赖(GraphRAG)场景启用;规模 <200 篇文件时优先 INDEX.md 导航 + 按需 Read。
- 中文语料必接 **jieba 分词**(FTS5 默认 unicode61 逐字切割,中文召回近零,research 坑 #12)。

**OpenViking 的用法**:面试谈资,不进技术栈。话术见 §7。

## 4. 核心引擎:doc-code drift 怎么检测

这是护城河所在,必须做深。整体遵循一条**核心工程原则**(业界 agentic coding 评测实践的共识,也是我前期调研的核心收敛):

> **"找线索(确定性)"与"做判断(LLM)"必须分离。把定位和判定扔给同一个 LLM,是误报不稳定的根本原因。**

所以引擎分**两层职责**,而不是"硬检测/软检测"两种手段:

### 4.1 定位层(确定性)—— 建立"文档声明 ↔ 代码事实"的精确对应

**只找线索,不下结论。** 用 tree-sitter/AST 把代码解析成结构化事实,用 FTS5/grep 精确匹配文档中的符号声明,产出对齐关系。**全程不碰 LLM,天然确定性、零幻觉、可作精确 ground truth。**

> **代码侧:不自己造解析器,复用开源。** 直接采用 OpenViking 式 `CodeSkeleton/FunctionSig/ClassSkeleton` schema(km 2756034031),`code_summary_mode=ast` 默认(纯确定,≥100 行才跳过 LLM)。原则"Parser 不调 LLM"与定位层一致。代码解析非本项目重点,当黑盒底座。

| 对齐项 | 代码侧(AST 提取) | 文档侧(抽取,见 §4.1.1) | 确定性 drift 判定 |
|---|---|---|---|
| 函数签名 | 参数名/数量/默认值 | 文档写的调用形式 | 参数对不上 |
| 返回类型 | 返回注解/推断 | 文档写的返回 | 类型不符 |
| 配置项 | 代码里的 config key | 文档列的配置 | 已删/未文档化 |
| 公开接口覆盖 | 所有 public 符号 | 文档提到的符号 | 差集 = 盲区 |

**关键契约:符号↔文档段落映射用结构化 ID,不用文本锚点**(research 坑 #10)。定位层输出 `{symbol_id, doc_anchor_id, code_loc, doc_loc}` 这样的结构化对齐记录,作为判定层的输入,避免接缝丢失。名不一致时的对齐见 §4.1.2。

#### 4.1.1 文档侧事实抽取管线(research 第二轮·缺口1)

文档侧比代码侧难(代码结构化、文档半结构化/散文)。**按文档类型分两条管线**,产物统一带来源标签 `ast/llm/fence`,drift 判定时区分可信度:

- **结构化 API 文档**(OpenAPI/Thrift/Markdown API 表)→ **三层解析,零 LLM,确定性**:
  - 结构层:heading 文本 + 代码块 `title` 属性定位"这是哪个方法/类型的声明";
  - 类型层:IDL 字段三元组(序号/类型/字段名)抽取事实;
  - 注释层:`///必传`、枚举名(常藏在 title 不在正文)、字段含义→**漏抽重灾区**。
  - 工具:remark 把 Markdown 转 mdast,API 表是 `table>tableRow>tableCell`(km 376430639)。
- **散文/docstring** → **LLM + JSON schema + 人工校准**(移植注入测评 L3,km 2770294827):抽 `(声明类型, 目标符号, 断言动作)` 三元组,校准门槛一致率≥90%、多次不一致<1.5%,**半确定性,产物标 `llm`**。

**两条铁律**:

1. **绝不依赖 heading 序号定位**——某 API 文档自身就有编号 drift(2.2.2 应为 2.1.2),必须用 heading 文本 + 代码块 title(km 1286970074)。
2. **抽取结果配验证机制**:借鉴 GBrain `verify_toc`(准确率高定点修复、低降级重试),drift 抽出事实后做一轮结构校验。
3. **若电子文档生成可控,优先"生而结构化"**:生成端强制 schema + `_schema` 版本号,从根上消除事后解析散文(km 2772176702)。

#### 4.1.2 符号对齐回退链(research 第二轮·缺口2)

§4.1 的结构化 ID 只解决"名一致怎么精确对齐"。名不一致(文档写 `username` 代码是 `user`、别名、重命名)时,走**五级回退链**,逐级降级、打置信度:

| 级 | 方法 | 置信度 | 层 |
|---|---|---|---|
| 1 | 精确名匹配(文档符号名 == 代码符号名) | 高 | 定位层 |
| 2 | FQN 匹配(`class:module.path:ClassName`,km 2708137250) | 高 | 定位层 |
| 3 | 签名指纹匹配(参数类型序列做指纹,差≤1 视为可能对齐) | 中高 | 定位层(AST 可确定性算) |
| 4 | embedding 语义相似度(声明句 vs 符号名+docstring,阈值≥0.85) | 中 | **判定层范围,不进 ground truth** |
| 5 | LLM 裁决兜底("这段声明是否对应这个符号") | 低 | 判定层,带置信度,低置信需人工确认 |

**配套**:

- **对齐单元 = 方法/类作用域内声明,不是全局名**(km 1286970074:同名 `ServiceStatus` 两个枚举重名,必须结合所属方法消歧)。
- 维护**别名表**(文档别名 ↔ 代码标准符号,km 2769059822 的 `userQuery/question/q-query` 模式);支持从 git history 追踪重命名(`git log --follow`/`-L`)。
- **证据不足不报 drift**:借鉴 GBrain `facts<3 或最老 fact<24h 则跳过`(km 2765788859),低置信对齐不直接产出 drift 告警。

### 4.2 判定层(LLM)—— 只在已对齐的符号对上判断"是否一致"

**只在定位层给出的对齐对上做语义判断**:函数行为描述与实现是否矛盾、示例代码是否还能跑通、两篇文档语义冲突。
- 必须**带证据锚点**(引用定位层给的 `code_loc` + `doc_loc`),不允许 LLM 自由发挥找问题。
- 防非确定性(research 坑 #2):固定种子/温度、结构化输出约束;能用确定性图 diff 判的绝不交给 LLM。

### 4.3 drift 四态模型(research §2.4,别人易漏第三态)

把所有 doc-code 关系归为四态。**处理方向按文档类型分叉**(见 §4.7):`code_derived` 类 drift→文档落后代码→改文档;`design` 类可能反过来→改代码;`contract` 类→报规约失效。

| 状态 | 含义 | 处理(以 code_derived 为例) |
|---|---|---|
| 文档有 ∧ 代码有 | 一致 or 冲突 | 判定层比对,冲突则报"过时/矛盾" |
| 文档有 ∧ 代码无 | **规约失效/文档过期**(drift 主战场) | 报过时,建议删除/更新(改文档) |
| 文档无 ∧ 代码有 | **知识缺失/盲区**(易漏的一态) | 报盲区,建议补文档("完备性即正确性") |
| 文档无 ∧ 代码无 | 无关 | 忽略 |

> 注:对 `design` 类文档,"文档有∧代码无"可能意味着**代码偏离设计**→修复方向是改代码而非删文档。真值方向决定每态处置,见 §4.7。

### 4.4 不可判定边界:显式标注,拒绝误报(research 坑 #3)

静态分析追不到的动态链路——MQ/事件回调、反射/DI、动态 SQL、MyBatis `#{}` vs `${}`、MapStruct/Convertor 字段映射——**一律产出 `unknown` 而非猜测**。"边界处标注不可判定"比"误报"更能体现工程成熟度,也是面试亮点。

### 4.5 置信度与降级

- 定位层确定性命中 → 高置信,直接报。
- 判定层 LLM 命中 → 中置信,带证据,可选人工确认(呼应美团"AI 触发 + 人工把关")。
- **索引陈旧即 drift**(research 坑 #4):检测器要**自报新鲜度**;索引落后源码时加"⚠️ 过期快照"提示直接读原文件,绝不静默返回过期结论。

## 4.6 输入管道:文档发现与解析触发(确定性,不归 agent 管)

引擎(§4)要能跑,前提是"知道文档/代码在哪 + 什么时候解析"。这一层**全是确定性管道,LLM/agent 不参与决策**——agent 只在最后判定环节登场。

### 文档怎么被发现
按可靠性排序,不互斥:
1. **约定优先**:扫固定位置——`docs/`、`README.md`、docstring、OpenAPI/Swagger,覆盖大多数。
2. **配置兜底**:`driftconfig`(或 CLI 参数)显式指明文档路径 + 代码路径,补约定扫不到的。
3. **不让 agent 猜文档在哪**——文档发现是确定性步骤,交给 LLM 会漏会错。

### 谁触发解析(不是 agent,是入口/事件)
解析是确定性流水线,由三个入口触发(对应 §5.5 三形态),不由 LLM 决定跑不跑:

| 入口 | 触发 | 解析粒度 |
|---|---|---|
| CLI | `drift-check ./repo` | 全量(首次)/全量或指定 |
| PR 门禁 / CI | git push 事件 | **增量**:只解析 diff 涉及文件 |
| MCP | Claude Code 调用 `check_drift` | 增量:指定变更文件 |

### 解析两种粒度

- **全量**:首次建索引,扫全库 docs+code,建 FTS5/符号表。跑一次。
- **增量**(常态):文件变更(git diff / 文件监听)触发,只重新解析变的文件(呼应 §4.5 保鲜)。

**完整链条**:入口(CLI/CI/MCP)→ 文档发现(约定+配置,确定性)→ 解析(全量首次/增量常态)→ 定位层建对齐(§4.1)→ 判定层(§4.2,agent 才登场)。

> 一句话:**文档位置靠约定+配置(不靠猜),解析靠事件触发(不靠 agent 决定)。** 前面全是确定性管道,agent 只做最后的语义判定。

### 4.6.1 符号级反向索引与增量重检(research 第二轮·缺口4)

§4.6 的增量只到**文件级**。要支持符号级 drift 重检测(改了 `login`,只重检引用它的文档段落,不全量),需自建**符号级反向索引**(学城材料不足,本项目自建):

**索引结构(代码符号 → 引用它的文档段落,倒排表)**:

```
主键: symbol_fqn (class:module.path:ClassName#method)
值:   { doc_id, doc_anchor(heading文本/代码块title),
       align_confidence, align_source(ast/embedding/llm),
       last_checked_at, last_code_hash }
```

这是 §5 `find_affected_docs(symbol)` 工具的实现底座。

**增量触发链**:git diff 拿变更文件 → AST 解析变更符号(增/删/改签名/改 docstring)→ 查反向索引得受影响文档段落 → 标 `stale` → 只重检这些对齐对(不全量)。

**幂等与重命名安全**(可迁移零件):
- `content_hash` 跳过未变内容(GBrain,km 2765788859);
- 重命名走 OMD 两层 schema——只更新符号 FQN 的路径段,不动 `content` 寻址的文档段落,避免误删重建;
- 删除顺序:先 `deleteVectorsBySource` 再 `deleteChunksBySource`,否则撞 UNIQUE constraint(km 2769059822);
- 增量调度状态机:`pending/processing/completed`,防重入、可观测(呼应 §6.3 Tracing)。

**生成式兜底**:对 `code_derived` 类文档,反向索引找不到对应段落时,直接从代码全量重生成该段作 ground truth 比对(km 376430639),比维护复杂映射更稳。

### 4.7 真值归属与文档类型分级(research 第二轮·缺口3)

**这是判定逻辑的地基,也是 arch 原有的一处隐错修正。**

**隐错**:原 §3"真值是代码和文档本身"不完整——**信源本身会 drift**:文件存在≠内容正确、schema 字段齐全(语法契约)≠字段有意义(语义契约)、信源本身会变成"第二真相源"(km 2772176702)。

**四道独立防线**(任一不过都告警,不因"文档存在"就默认通过):

1. 存在性(文档/代码在不在)
2. 语法有效(字段齐全、格式对)
3. 语义合理(内容有意义)
4. 与代码同步(没落后/偏离)

**按文档类型区分真值方向**(km 376430639 + 1286970074 收敛):

| 文档类型 | 含义 | 真值方向 | drift 含义 | 修复方向 |
|---|---|---|---|---|
| `code_derived` | API/IDL/签名表(能从代码机械派生) | **代码为准** | 文档落后代码 | 改文档(重生成) |
| `design` | 设计/需求文档(非派生) | **文档为准/双向** | 代码偏离文档意图 | 可能改代码 |
| `contract` | 契约/规约 | **契约为准** | 代码违反规约 | 报规约失效 |

这直接决定 §4.3 四态里每态的处置语义(改文档 vs 改代码 vs 报失效)。

**判定分层落到真值层**(km 2770294827):LLM 只负责解析文档语义,**确定性规则判 drift**(签名比对/参数差集/覆盖差集),不用 LLM 验 LLM 抽取结果——避免循环验证。

## 5. 架构:Multi-Agent 编排

```
             ┌────────────────┐
用户/定时触发 →│ Supervisor     │ 决定调度顺序、汇总结论
             └───────┬────────┘
                     │
       ┌─────────────┼─────────────┬─────────────┐
       ▼             ▼             ▼             ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│检索 Agent│  │代码解析  │  │一致性审查│  │报告 Agent│
│(RAG)     │  │Agent(AST)│  │Agent     │  │          │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
    └── 取相关文档 + 对应代码 ─┘ → 4.1/4.2 检测 → 健康报告
                                  ↑ ↓
                           ┌────────────┐
                           │ Memory 层  │ drift 历史/盲区/bad case
                           └────────────┘
```

**各 Agent 职责**:
- **检索 Agent**:Agentic RAG,不是固定"查一次",而是 agent 决定要不要查、查几跳(文档→引用的代码→调用方)。**多跳依赖追踪走 GraphRAG**(代码调用链天然是图,research §4:图信号使 P@5 17.7%→49.1%),检索是工具,控制权在 agent。
- **代码解析 Agent = 定位层(§4.1)**:tree-sitter AST 提取结构化事实 + 复用 GitNexus/CodeGraph 式图原语(`callers/callees/impact/detect_changes`)做变更影响分析(SCA 肌肉)。可封装为工具/MCP server(想秀跨语言可用 Java 写,非必需)。
- **一致性审查 Agent = 判定层(§4.2)**:只在定位层给的对齐对上跑 LLM 语义判定,产出带证据的 drift 列表 + 四态分类。
- **报告 Agent**:聚合成健康报告(过时/矛盾/盲区 + 健康分 + 新鲜度)。
- **Supervisor**:编排调度、汇总(对齐大厂 supervisor/handoff 心智)。

> 架构映射:检索 Agent + 代码解析 Agent = **定位层(确定性)**;一致性审查 Agent = **判定层(LLM)**。二者物理分离,正是 §4 核心方法论的落地。

## 5.5 应用形态与触发方式

**先澄清定位**:本项目**不是**"在 Claude Code 里帮你写代码"的工具,而是"你(或 Claude Code)改完代码后,检查文档有没有跟上"的工具。它站在编码流程的**下游/旁路**,不是编码本身。

三种形态,本质是**同一个核心引擎 + 三层皮**,不是三选一:

```
┌──────────────────────────────────────────┐
│ 核心引擎(定位层 §4.1 + 判定层 §4.2 + 四态) │ ← 真正的价值,先做
└──────────────────────────────────────────┘
           │              │              │
           ▼              ▼              ▼
      [C] CLI       [B] MCP Server   [A] CI/PR 门禁
       手动跑       Claude Code 调用    git push 触发
      最好 demo      命中 MCP 硬通货    最强护城河叙事
```

| 形态 | 触发方式 | 优点 | 缺点 | 对应阶段 |
|---|---|---|---|---|
| **C. CLI** | 手动 `drift-check ./repo` | 最好 demo、最易开发,是 A/B 的内核 | 单看是"扫描工具",agent 味不足 | MVP~v2 |
| **B. MCP Server** | ①Claude Code agent 主动调用(CLAUDE.md 约定)②手动 `check drift` | **命中 MCP 硬通货**;与"用 Claude Code 写代码"无缝;demo 直观 | 依赖 agent 主动调用,触发不稳定 | v3 |
| **A. PR 门禁 / CI** | git push / PR 事件全自动 | **最强护城河叙事**(美团"文档评审机器人"设想的实现);持续同步闭环,不靠人记得 | demo 需真实 repo + CI | v3+ 亮点 |

### 直接回答:"我用 Claude Code / Codex 写代码,怎么触发这套流程?"

**两条触发路径,建议都做,展示两种范式:**

1. **主动式(in-loop,形态 B)**:drift 检测器做成 MCP server 挂到 Claude Code。在项目 `CLAUDE.md` 里写一条约定——"每次修改公开接口/函数签名后,调用 drift 的 `check_drift` 工具检查文档"。Claude Code 改完代码会自己调;或你手动 `帮我 check drift`。
   - 暴露的工具:`check_drift(changed_files)`、`find_affected_docs(symbol)`。
2. **被动式(out-of-loop 兜底,形态 A)**:你不用记得。Claude Code 写完 → 提 PR → CI 自动跑 drift → 结果直接评论在 PR 上("你改了 `login()` 加了参数,但 `docs/auth.md:20` 还是旧签名"),可选自动提交文档更新 PR。

**为什么两条都要**:主动式依赖模型"记得调用"(不可靠);被动式是**兜底闭环**,不依赖模型主动性,才是真正保证"文档不烂"的那道关。

> **面试话术**:"它有两种触发——主动式做成 MCP,Claude Code 编码时可调用,是 in-loop 辅助;被动式做成 PR 门禁,push 后自动检查,是 out-of-loop 兜底。兜底那条不依赖模型主动性,是真正保证文档不烂的持续同步闭环。"

## 6. Memory + 评测飞轮(差异化钩子)

### 6.1 分层记忆

| 层 | 内容 | 作用 |
|---|---|---|
| 短期(会话) | 当前检测任务上下文,"阈值+比例"压缩 | 控上下文长度 |
| 长期(持久化) | drift 历史、已确认盲区、被判过时的文档清单 | 越用越懂这个库,避免重复报 |
| 运行时注入 | 把长期记忆里的"已知盲区/历史 drift"注入当前检测 | 增量检测,不从零 |

### 6.2 评测体系(你的独有贡献,做成核心亮点)

核心原则:**"先修评测再改 Agent"**——评测本身可信,才敢改引擎。

**A. 检测引擎本身准不准(硬指标,有 ground truth)**
- **分层评测集**(research 坑 #7:纯 RAG 准确率天花板 <60%,根因就是评测集不分层):按 drift 类型(签名/返回/配置/盲区/语义)+ 难度分层构造。
- 构造方式:①手动注入 drift(改文档制造已知不一致);②**挖真实 commit 历史**里"改了代码没改文档"的提交对(更真实,bad case 有血肉)。
- **准确率 + 召回率**:定位层有确定性 ground truth,可精确算。
- **三级 Grader**:Code(grep/AST 确定性)+ Model(llm_judge 3 票多数)+ Human(金标,Kappa≥0.7 校准)。
- **防评测作弊/失真**(research 坑 #8):`denom_max` 反事实调分母陷阱(用 n/a 缩小分母刷高分);LLM judge 限流返回 unknown 要显式处理不能算过;明确 grader 度量的是定位层还是判定层。

**B. 知识库健康度(软指标,对齐美团三指标)**
- 过时率、矛盾数、覆盖盲区数、健康分。
- **数据飞轮**:bad case(漏检/误报)→ 回流成新评测样本 → 引擎迭代;查询侧"查了没答案"→ 待补文档清单。
- **A/B 对比范式**(research §2.6):有 drift 检测 vs 无,量化提升(参考知识图谱增强代码生成 73% vs 42% 的对比实验设计)。

**C. 度量方法补强**:若用编辑距离(Levenshtein)判相似,**必须辅以 AST 结构级比对**——编辑距离对重命名/等价改写会误判(research 坑,km 2712884923)。

### 6.3 Tracing

每次检测的 trajectory 可追溯:Supervisor 决策 → 各 agent span → 具体检测项 → 证据锚点。对标 JD"评测看 trajectory 而非黑盒"。

## 6.5 保鲜机制与触发方式(research §2.5 + km 2725725083 方向二)

drift 检测不是一次性扫描,而是**持续同步闭环**——这是区别于"文档生成工具"的关键。

**保鲜(低成本感知变更)**:
- 文件监听(FSEvents/inotify)+ 2s 防抖,增量重分析变更文件。
- git hash 对比 HEAD + 内容哈希,检测离线期(git pull/他人编辑)变更并补建。增量 Token 约全量 5–15%。

**触发挂载点**(事件驱动,km 2746384780):
- 保存文件 / PR 提交 / CI failed / Release → 自动触发 drift 校验。
- **PR 门禁形态**(最强落地叙事):PR 阶段跑 drift 检测,发现文档滞后 → 自动产出"文档更新 PR"或评论。这正是美团调研里"文档检测智能评审机器人"设想的实现。

## 7. 面试话术(预置三个必被问到的问题)

**Q:这个为什么不用 Claude Code 直接做?**
> 查文档 Claude Code 确实能做。但我的项目不是查文档,是**逐条比对整个项目的文档和代码、精确找出所有不一致**。这需要 AST 级解析代码结构(每个函数几个参数、返回什么类型),再和文档声明做确定性比对——这是一个专门的分析引擎干的活,通用 agent 聊天聊不出来,也不会主动去跑全库交叉验证。

**Q:字节 OpenViking / 美团知识库不是做了吗?**
> 检索这层确实商品化了——字节开源 OpenViking,美团也迁到魔改版。所以我没在检索层重复造轮子,用 Qdrant 做等价检索。我把精力放在**它们一笔带过的地方**:文档-代码语义级 drift 检查。美团的知识保鲜方案是事件驱动 + 人工审核,没有自动化精确检测引擎——这是我做深的缺口。

**Q:和你的 SCA 项目啥区别?**
> 同一套"读懂整个代码项目结构"的静态分析能力,换了靶子:SCA 扫代码找 bug,这个扫文档-代码找 drift。能力同源、产出不同。而且这个项目额外补齐了 RAG、Multi-Agent、分层记忆、评测飞轮——是我 agent 工程能力的完整拼图。

**Q:LLM 判 drift 会不会误报很多?怎么保证可信?(会被深挖)**
> 这正是我架构的核心。我把"找线索"和"做判断"物理分离:定位层用 AST + FTS5 做确定性对齐,完全不碰 LLM;LLM 只在已对齐的符号对上判"是否一致",而且必须带证据锚点。把定位和判定丢给同一个 LLM 才是误报的根本原因。追不到的动态链路(MQ/反射/动态SQL)我显式标 unknown 而不是猜。再加上"先评测再改引擎"——我有分层评测集和三级 Grader,先保证检测器本身可信,才敢迭代它。

## 8. 落地路线(MVP → 完整)

| 阶段 | 内容 | 产出 | 形态 |
|---|---|---|---|
| **MVP** | 单文件级:一个函数的文档 vs AST 签名定位层检测 | 能跑通"检出参数不一致" | C(CLI) |

| **v2** | 加判定层(LLM 语义)+ 四态 + 证据锚点 + 不可判定边界 | 覆盖行为/示例矛盾 | C(CLI) |
